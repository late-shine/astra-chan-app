## Notes on heuristics used

- "Declared reading with no matching example" and "example reading not covered" both use plain
  substring matching between a declared reading's stem (okurigana dash stripped, katakana normalized
  to hiragana for onyomi) and the kana in an example's "(...)" parenthetical. This is intentionally
  the same kind of comparison the real quick-list fallback in KanjiScrollScreen.tsx does — reused here
  only as an offline audit signal, never as runtime lookup logic.
- For single-kanji-plus-okurigana examples (e.g. "生きる" for 生) this comparison is reliable —
  marked `[confidence: high]`.
- For multi-kanji compound examples (e.g. "日本" for 日) the comparison can only check whether *some*
  declared stem appears anywhere in the compound's reading, which cannot prove which kanji contributed
  which syllables. Many of these are legitimate onyomi-variant/rendaku/jukujikun readings, not data
  errors — marked `[confidence: low (compound word)]` and meant for human triage, not as a claim that
  every low-confidence line is a bug.
- The duplicate-card-key check is not one of the plan's original audit bullets; it was added because
  it falls out of the same data pass at negligible cost.
