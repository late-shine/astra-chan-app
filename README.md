## The Story

This didn't start as a project. It started as a small experiment while Ashraful and I were learning Japanese.

I opened Claude and asked it to make a simple quiz. Ashraful was the one who asked, *"Can it add sound effects? Let me try."* It worked, so I tried too. Then came the dangerous question: *"Let's make it bigger. Let's see what it makes."*

That is how a tiny quiz became Astra-chan.

Ashraful and I did not build one app together. We built our own separate apps. We shared plans, features, ideas, and the architecture underneath them. When one of us tried something interesting, the other would borrow the idea, improve it, or argue for a better version. There was no gatekeeping; we regularly pushed each other to take good advice. Astra-chan is my app, but that shared creative pressure is part of its story.

What followed was about a week of intense building — roughly 4 to 5 hours every day, sometimes more. I became completely absorbed in breaking things, fixing them, adding features, redesigning them, and occasionally breaking them again. By the time I first uploaded it to GitHub, around 8 days had passed. Not months. One focused, obsessive week.

I did not write the code line by line myself. I decided what to build, how it should feel, what was worth adding and what was not, when something looked wrong, and when a technically impressive idea would make the app worse for a beginner. The project taught me that knowing *what to ask*, what to reject, and what to test is its own skill.

The app grew from a single HTML file into a full-stack learning space with multiplayer, AI-assisted kanji drawing feedback, spaced repetition, Firebase sync, grammar and reference tools, reading practice, and a mascot companion named **Astra-chan** — whose artwork was generated by Gemini after many, many attempts.

### How I work with AI

I use AI as a group of collaborators, not as an autopilot. Different models help with architecture, implementation, research, design criticism, and verification, but I make the product decisions and test the result in the running app.

The workflow evolved over time. I first used one model to build and verify. Later I separated planning from implementation, and eventually separated building from verification. That made it easier to catch assumptions, compare different approaches, and keep Astra's visual language consistent.

Large changes now move through a small, repeatable loop: define a phase, keep a current context file and codebase map, let one builder implement the phase and write a handoff, have a different verifier inspect the actual diff, then run the commands and browser checks myself. Fresh AI sessions can continue from the handoff without rereading the whole project.

This process is slower than accepting the first generated answer, but it makes the app easier to improve without losing track of what changed.

Some moments worth mentioning:

- When the background images and music came together for the first time, something clicked. It stopped feeling like a quiz app and started feeling like a *place*.
- Different models kept different parts of the project honest. One would propose a design, another would find the confusing part, and I would test the result before deciding whether either suggestion belonged in the app.
- The multiplayer system took the longest. I checked Firebase guidance with more than one model and researched API-key security before trusting the deployment. Nothing important was accepted just because one model sounded confident.
- The Study Room redesign changed everything. Instead of menus and tabs, the home screen became Astra-chan's room — a Bookshelf, a Writing Desk, a Star Window. Navigation as a place to be, not a list to scroll through.
- Astra-chan now reacts when you go AFK. She starts wondering after 15 seconds of silence, shifts into deep AFK after 35 seconds total, and lights up when you return. She also reacts while you practise: focused during a question, pleased after a correct answer, encouraging after a mistake or timeout, and supportive after repeated misses when you pause.
- The kanji drawing feedback went through two model generations. The original used Cloudflare Workers AI with LLaVA 1.5 7B — a vision model that technically worked, but gave vague or inaccurate structural feedback. I switched it to **Google Gemini**, now using a fallback chain beginning with Gemini 3.8 Flash and stepping through 3.6 Flash, 3.5 Flash-Lite, 3.1 Flash-Lite, and the 2.5 Flash models when a model is unavailable, rate-limited, or too slow (each attempt has its own time limit, so the checker answers within about 35 seconds). The feedback stays specific enough to explain what looked off, alongside a separate KanjiVG-based stroke demonstration.

This is still being built. It probably always will be.

### Splitting App.tsx — a case study in AI-directed refactoring

This section describes an earlier refactor. The current quiz screens share QuizFlow/Duel views; superseded screens and the development-only prototype are no longer part of the app.

By the time the feature list above was mostly done, `App.tsx` had grown to
**7,625 lines** — one giant component holding ~90 pieces of state and every
screen's JSX in a single function scope. It worked, but it was becoming
impossible to hand to any AI session without burning half the context
window just reading it.

The fix took **9 phases**, each one extracting a single screen
(`menu`, `results`, `vocab-quiz`, `kanji-quiz`, `quiz`, `kanji-scroll`,
`profile`, `review-deck`, `online-multiplayer`) into its own component under
`src/components/`, using plain prop-passing — no Context, no state
libraries, nothing that would risk subtly changing behavior.

The workflow for each phase:
1. One Claude session (the reviewing Claude) reads the current `App.tsx`,
   identifies the next screen's exact line boundaries and every piece of
   state/handler it touches, and writes a detailed, scoped prompt — what to
   read, what *not* to read, what must never move, and the exact output
   format expected.
2. That prompt gets handed to Codex, which does the actual extraction.
3. The result comes back to Claude for verification (line counts, bracket
   balance, cross-screen state checks) before moving to the next phase.

A few things made this harder than "just move the JSX":
- Several screens shared state with each other — `currentKanjiIndex` was
  used both inside the `kanji-scroll` screen and in the mascot companion
  render outside it; the friend-invite system was shared between `profile`
  and `online-multiplayer`. Each had to be identified and kept in `App.tsx`,
  passed down as props to both consumers, rather than moved.
- The `online-multiplayer` screen (the final and biggest phase, ~983 lines)
  had state driven by `useEffect` hooks handling Firebase room
  subscriptions — logic that had to stay in `App.tsx` regardless of where
  the JSX lived, which inverted the usual "move anything self-contained"
  instinct from every earlier phase.
- One early Codex session burned through its usage limit fighting its own
  PowerShell string-escaping and a self-created symlink to an external
  `node_modules` folder, without producing a final result. The fix wasn't a
  cleverer prompt — it was adding an explicit "work efficiently" section to
  every prompt after that: no scripted string replacement, no full
  project-wide lint/build runs chasing unrelated pre-existing errors, do the
  edit once.

End result: `App.tsx` was cut nearly in half, with 9 new screen components and zero behavior changes — verified phase by phase by actually clicking through the app, not just trusting a clean build.

### Rebuilding the Review Deck — a case study in phased, verified changes

The first spaced repetition system worked, but it was simple: five levels, a wrong answer dropped a card one level, and tapping the Review Box started a session with **every** due card. After a few weeks away that could mean hundreds of cards in one sitting, which is the fastest way to make someone stop reviewing.

I did not ask for a rewrite in one go. An earlier plan from another AI was checked against the real code and revised, and the work became **five phases**:

| Phase | What it changed |
|---|---|
| **S1** | A pure scheduling engine (`src/srsScheduler.ts`) with a nine-step ladder, and a safer cross-device merge based on last review time instead of due time |
| **S2** | A daily session: limits for reviews and new cards, a 10-minute relearn step, and honest "Today" counts |
| **S3** | Three grades (Forgot / Hard / Got it), per-card ease, interval previews, a level ring and a 7-day forecast |
| **S4** | Tricky cards that are set aside after repeated misses, and an optional backlog recovery tool |
| **S5** | Fixing a key collision so the kanji 山 and the word 山 can both be cards, with a migration for existing decks |

How it was kept safe:
- The scheduler is a plain module with no React, storage, or Firebase inside it, so it can be tested alone. `scripts/srs-sim.ts` replays decks and a 365-day simulation as a long list of checks; it can also read an exported backup and report what would change, without writing anything.
- Existing decks had to load unchanged: every card keeps its level and due time, and new fields are optional.
- One Claude session built each phase and a separate one reviewed it. I ran the real lint, build, and simulation checks, then used the running app. Several decisions came from that last step, not from the code: after a real session, I noticed a forgotten card could come back three times and, near the end of a session, straight away. That became a written open decision instead of a silent change.
- The S5 problem was found by reading the code before building (41 vocabulary words are also single kanji), so it was planned as its own phase with a migration rather than patched in passing.

### 🎯 Practice & Quiz

Practice opens **Rainlit Atelier**: Astra's rainy nighttime study room, with one recommended session and secondary Customize/challenge controls. The visual scope covers Practice, quiz setup/player/recovery/results and friendly duels. Study Room, Learn, Grammar, Reading and SRS retain their existing interfaces. Every saved theme ID uses the same night palette inside the atelier. Phone artwork and speech share one bounded companion panel; no portrait-position/size editor ships.

- **Untimed normal practice**, correct-only auto-next ON by default after1.6s. Wrong answers/timeouts wait for Next; interaction can pause auto-next. Timed and Survival have explicit clocks rather than hidden adaptive difficulty.
- **Kana:** read, pick kana, type romaji or Mixed; Hiragana/Katakana/Both and Core/Dakuten/Handakuten/Yōon groups. Four choices, with an acknowledged six-choice option for eligible kana pools. Typed aliases are item-specific, not fuzzy matching.
- **Words:** Meaning, Reading, Reverse or Mixed; public themes, manually Learned words and custom selections. Reading does not reveal its reading/audio before grading.
- **Kanji:** Meaning, On’yomi, Kun’yomi, isolated Mixed, and explicit **In words · Curated set**. The current audited context pool supports60 distinct whole words from13 families/64 source entries. In words teaches the complete reading, not invented per-kanji segmentation.
- **Length:**10 /20 /30 /All eligible targets. Ordinary sessions use each selected target once, including Mixed. All is blocked if the eligible pool exceeds the existing256-question recovery bound; it is not silently truncated. Survival repeats its frozen bank.
- **Challenges:** solo timed Kana12/6/3s, Words/Kanji20/10s; Survival is kana choice with45s initial budget,60s cap, correct+5s and wrong−8s. Survival correct feedback uses0.9s; mistakes remain manual.
- **Growth:** first-try accuracy stays separate from repair. Practice remaining misses in batches of up to5 frozen same-kind questions. Add missed items to Review Deck explicitly, with dedupe and existing daily introduction limits; adding a card does not schedule an immediate introduction.
- **Astra's dialogue:** locally authored English and decorative expressions, not AI chat/TTS. During solo quizzes she responds to the current question, correct answers, mistakes, timeouts, results, and repeated misses. A third consecutive solo mistake can offer gentle support within a cooldown/cap; timed/Survival support waits for explicit pause. Her reactions do not change questions, difficulty, rewards or clocks, and duels use generic entry/results only.
- **Manual mastery stays manual:** word quiz answers never tick garden learned flags; kanji quiz answers never consume the separate once-per-kanji Study+40 reward or change manual mastery. Kana first-pass practice still updates its glyph accuracy.

#### Quiz XP

| Accepted record | XP |
|---|---|
| Ordinary/timed correct choice |15; Quick+5, kana Lightning+10 |
| Ordinary/timed correct typed kana |25; same timed bonuses |
| Survival correct choice |15 |
| Correct repair |5; repair counters only |
| Completed ordinary/timed practice with≥10 unique first-pass targets |20 once |
| Duel own accepted correct choice / typed kana |15 /25; Hard+5, kana Superhard+10 |
| Wrong, timeout, unattempted |0 |

No response-speed multiplier or win bonus. Partial/repair/Survival/duel sessions have no completion bonus. First-pass wrong/timeout still counts as an attempt and study activity; opponent-claimed/unshown duel rounds do not. Repair does not inflate global first-try attempts/accuracy.

#### Saving and recovery

A confirmed local save writes progress and its receipt together. **Saved on this device** is separate from **cloud sync pending**. Account records queue for the existing cloud writer; refresh/reconnect uses ordered receipts rather than paying the same answer twice. Recovery is owner-scoped, with a24h/512KiB solo snapshot and a separate bounded current-duel learning journal, so a duel does not overwrite saved solo practice. Backup import replaces current-owner recovery/outbox state before adopting imported totals; browsing old history does not replay rewards.

Storage-denied/full browsers show Retry and an explicit Continue without recovery choice. In-memory progress can be lost when the page closes. No fresh offline-install cache or service worker is promised: locally loaded quiz content can work without network, while a first uncached page load still needs its assets. Existing aggregate cross-device merging does not guarantee an exact history when multiple devices study concurrently.

The separate **Kanji Practice Station** still provides Watch /Trace /Write /Review with optional AI-assisted drawing feedback, real stroke paths and the existing reduced-motion controls. It is outside the quiz engine. The learning Word Family panel remains a curated reference, not an exhaustive dictionary.

### 🔁 Spaced Repetition (SRS)
- **Personal Review Deck** — add any word or kanji, or the words you missed in the Reading Room. A kanji and a word that share a character (like 山) are separate cards
- **Nine-step schedule** — 8 hours → 1 → 3 → 7 → 14 → 30 → 60 → 120 → 240 days (never more than a year), with a small ±12% spread on longer intervals so cards do not all return on the same day
- **Three-button grading** — **Forgot / Hard / Got it**, each showing when the card will come back. Every card also remembers how easy you find it, so easy cards space out faster and hard ones return sooner
- **Relearning** — a forgotten card drops back and returns later in the same session (about ten minutes later); the re-show earns no extra XP
- **A session that fits in a day** — 50 reviews and 10 new cards by default, adjustable from the gear in the Review Deck (up to no limit). The home screen shows a line like "Today: 25 reviews · 5 new · about 5 min", extra cards simply wait, and "Study N more" is there when you want to go further
- **Level ring and 7-day forecast** — see how well a card is known, and how many reviews are coming over the next week
- **Tricky cards** — a card you have forgotten six times is set aside so it stops crowding your sessions. A small flag opens the list, where you can put a card back (starting again at level 0) or remove it
- **Backlog recovery** — if you have been away and are far behind, an optional tool, with a confirmation that shows the exact number, spreads the most overdue cards over the coming days instead of facing you with one huge pile
- **Safe with old data and across devices** — decks from before the rebuild load with their levels and due dates intact; signed-in devices merge by most recent review instead of overwriting each other; the daily limits follow your account
- XP is awarded for every first-time answer in a session, and total reviews count toward badges like *Deck Master*

### 🌐 Online Multiplayer

Friendly two-player **protocol2** rooms use a6-character code and the atelier. Both players agree on the current public set and press Ready; changing subject, type, timer or set clears both readiness states. Both clients should update/refresh; old-protocol rooms are rejected before joining.

- **Supported:** Kana read/type; Words meaning/reading/reverse; Kanji meaning/on. Four choices; no mixed, audio, kun or context questions in duels. Public all/theme/explicit sets only; no shared knowledge or learned/studied comparison.
- **Counts:**5 /10 /20, shrinking to the actual eligible unique targets; minimum5. The host freezes every question and option/order once, and the guest plays that snapshot.
- **Competitive:** first accepted correct claims one match point; a round already claimed before you answer is unattempted. Two wrong answers or expiry can resolve without a point. Shared starts/deadlines keep running through hidden tabs/disconnections.
- **Parallel:** independently answer the complete set. Correct count wins, then lower total response time across all answers, including full-duration timeouts; exact equality ties. Words/Kanji default to Parallel.
- **Timers:** Kana15/10/5/3s; Words/Kanji20/15/10s, no Superhard. Both modes are available.
- **Recovery/results:** per-connection presence and persisted index/deadline; explicit leave or qualifying connection loss gives partial counts with no invented winner. Rematch keeps members but clears the old manifest/answers/Ready and creates a fresh match ID. History uses that ID, records actual totals/partial status, and leaves older entries readable.
- **Personal learning:** only confirmed own correct/wrong/timeout records affect your study progress. Match points and study XP are separate. No win/completion bonus; Practice my misses uses actual own misses and is disabled with an explanation when local catalog mapping is unavailable.
- Existing friend requests, notifications, room invites and response tracking remain. No learning history is published for set selection.

## What I Learned

- How to break a large problem into phases small enough for an AI to handle reliably
- That a prompt isn't memory — plans, context files, and handoffs are what let a brand-new chat pick up where the last one stopped
- When to trust an AI's output and when to verify it with a different one
- That "it passed" and "it's right" are different sentences — a clean build can't tell you whether the screen actually looks right
- That a simulation script catches what clicking around can't (a year of reviews in seconds), and clicking around catches what the script can't (a card coming back three times in one sitting)
- That design decisions, product decisions, and debugging instincts can't be delegated — those stayed with me
- That building something for yourself, for a real reason, makes every frustrating session worth it
- That the best portfolio piece isn't the most technically impressive one — it's the one with a real story behind it
- That one focused week, if you care enough, can produce something you're genuinely proud of

## Setup (Local Development)

> **Known requirements:** multiplayer needs Firebase Realtime Database and Firebase Anonymous Auth. Cross-device progress sync additionally requires Firebase Email/Password or Google Auth and the private `userProgress/$uid` database rule. Kanji-drawing AI feedback and the optional fixed Gemini voice catalog use the server-side Google Gemini API key; browser voices remain available without it.

```bash
git clone https://github.com/late-shine/astra-chan-app.git
cd astra-chan-app
npm install
cp .env.example .env
# Fill in your Firebase and Gemini API keys
npm run dev
```

### Environment Variables
```
VITE_FIREBASE_API_KEY=
VITE_FIREBASE_AUTH_DOMAIN=
VITE_FIREBASE_PROJECT_ID=
VITE_FIREBASE_DATABASE_URL=
VITE_FIREBASE_STORAGE_BUCKET=
VITE_FIREBASE_MESSAGING_SENDER_ID=
VITE_FIREBASE_APP_ID=
GEMINI_API_KEY=
GEMINI_TTS_MODEL=gemini-3.8-flash-lite-tts
```

Enable **Email/Password** and **Google** under Firebase Console → **Authentication → Sign-in method** if you want account creation and cloud progress sync. Password-reset emails use Firebase Authentication's built-in email action and can be customized under **Authentication → Templates**. Apply the complete rules from `database.rules.json` to Firebase Realtime Database. The `userProgress/$uid` path is private to the authenticated owner.

When using the Firebase CLI, publish database rules with:

```bash
firebase deploy --only database
```

For the fixed Astra Gemini voice catalog, add the same server-side `GEMINI_API_KEY` to the local `.env` file and Vercel Environment Variables. `GEMINI_TTS_MODEL` is optional and defaults to `gemini-3.8-flash-lite-tts`; the server falls back through Gemini 3.8 Flash TTS, Gemini 3.1 Flash TTS, and Gemini 2.5 Flash TTS when the selected model is unavailable or rate-limited. Never use a `VITE_` prefix for the Gemini key. If every Gemini TTS attempt is unavailable, Astra falls back to the browser voice engine.

> Get a free Gemini API key at [aistudio.google.com](https://aistudio.google.com). Gemini limits vary by model, project, and time window; if the voice quota is reached, Astra automatically uses the browser voice instead.

> ⚠️ **AI drawing analysis limit:** The drawing checker tries several Gemini Flash models when one is unavailable, rate-limited, or slow. On Google's free tier the two strongest models allow only about 20 requests per day each, so most checks end up on the Flash-Lite models; if every quota is used up, the checker shows a friendly message until a window resets. The chain can be changed without a code edit via the optional `GEMINI_ANALYSIS_MODELS` environment variable.

The ordinary app mounts the regular experience in both development and production builds.

### Firebase Realtime Database Paths

Online multiplayer and account sync use Firebase Authentication and these Realtime Database paths:

- `rooms`
- `friends`
- `friendRequests`
- `invites`
- `inviteResponses`
- `matchHistory`
- `userProfiles`
- `userProgress` — private study-progress record for each signed-in account

`matchHistory` records finalized protocol2 matches by fresh match ID, including partial endings with a manifest. Older entries remain readable; missing historical matches/rewards are not reconstructed retroactively.

### Multiplayer security boundary

Authentication/rules protect membership IDs, invite ownership, profiles and private progress paths. The client derives answer role from the authenticated UID. However, participants have parent-level room write grants: manifests, grading and timing remain friendly **client-scored** data, not a server referee or tournament anti-cheat guarantee. Signed-in users with a waiting-room code can read its public setup; rematch removes old question/answer payloads before waiting. Public set agreement never compares private learning histories.

The app adds no new database path or rules change in the current release. Existing installations do not need a Firebase console re-paste; fresh Firebase projects still need the checked-in rules during initial setup. If a future change edits `database.rules.json`, update the Firebase console as part of that change. Pending sync and existing concurrent-device aggregate merge limits still apply.
